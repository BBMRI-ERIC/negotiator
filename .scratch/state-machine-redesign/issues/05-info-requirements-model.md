# Information requirements as first-class model

Type: grilling

Blocked by: 01, 03

Status: resolved

## Question

Redesign `eu.bbmri_eric.negotiator.info_requirement`/`info_submission` (today: `InformationRequirement` ties an `AccessForm` to a `NegotiationResourceEvent`, enforced ad hoc inside `ResourceLifecycleServiceImpl.sendEvent()`, Resource-lifecycle only) so information requirements are a first-class part of the definition model from ticket 01, for *both* the Negotiation-level and Resource-level lifecycles.

Decide:

- How a requirement attaches to an Event in the new data-driven definition.
- How enforcement is expressed — still an imperative check in a service method, or declarative within the definition itself (e.g. evaluated by the engine as part of the transition guard chain). Per ticket 03 (Engine choice), the engine is a stateless evaluator with a guard/action registry — decide whether info-requirement satisfaction becomes a registry guard type, or stays a distinct check type alongside it (see next bullet for why these aren't necessarily the same thing).
- The API/contract question this raises: today `getPossibleEvents()` filters only by source-state and authority (never checks info-requirements), while `sendEvent()` gates on requirements separately and earlier — so an event can display as available/clickable and then fail on submission if its form hasn't been filled in (a live UX bug). Decide whether the new contract keeps that decoupling (possible-events unaffected by requirements, requirements still a separate late gate) or unifies them (e.g. possible-events returns per-event requirement status so the FE can render "needs form X" instead of a dead click), and design whatever shape is chosen.
- Whether `InformationSubmission`'s existing shape (JSONB payload keyed to resource/negotiation) carries over unchanged, or needs to change to fit the new attachment model.

## Answer

**Attachment shape.** A `Requirement` row attaches to an `Event` (per ticket 01), 0..N per event, unordered — no dependency between the forms attached to one event, and no per-source-state variation (preserves "applies wherever this event fires," ticket 01's reason for choosing Event over Transition).

**Assignee.** Today's model has no concept of *who* a requirement applies to beyond an implicit "any representative of the resource." The new `Requirement` gets an explicit assignee, one of: the resource's representative(s) (kept as the default "system" audience), a specific `Person`, or a `Group` — where `Group` here is a **lightweight reference only** (id/external-group-key, name), enough to mirror an IdP group, with no group-management/membership-sync mechanics designed here. Satisfaction for a group- or person-assigned requirement is "at least one qualifying submission exists from within the assigned audience" — matching today's actual (non-disambiguated) behavior. Full `Group` design (IdP sync, membership resolution, other places it'd be used) and the joint-vs-individual multi-person submission modes are explicitly **out of scope for this ticket** — moved to the map's "Not yet specified" as a future effort, per the user's own scoping call.

**Enforcement: a real `GuardType`, not a separate check concept.** Reversing the initial recommendation in this ticket's discussion: info-requirement satisfaction is implemented as a registry `GuardType` entry (parameterized by the Event's attached Requirements), evaluated inside the same guard chain as any other guard — not as a distinct third enforcement concept alongside guards and `required_authority`. This was confirmed feasible by investigating Spring Statemachine: `getPossibleEvents()` today is pure app code (not a framework method) that only checks `SecurityRule`, and never calls `Transition.getGuard()`; but `Guard.evaluate()` is a pure, side-effect-free predicate (confirmed via bytecode: `AbstractTransition` treats a throwing guard as a deny, i.e. as a query, not a commit), so it is safe to dry-run.

**One evaluation pipeline, used for both the real gate and the dry-run listing.** Today's code has an actual double-enforcement bug: `ResourceLifecycleServiceImpl.isSecurityRuleMet()` is hand-checked once to build `getPossibleEvents()`, then Spring Statemachine's own `.secured()` interceptor checks the same rule again when `sendEvent()` fires. The new engine exposes one `evaluate(definition, currentState, event, context) -> TransitionEvaluation` function, called identically by `sendEvent` (the real gate) and by the possible-events listing (a dry run over every event reachable from the current state) — no parallel reimplementation. `required_authority` stays a distinct field per ticket 01 (not folded into the guard list), but is evaluated as step one of this same single pipeline rather than as a separate hand-rolled pre-check.

**Guard contract returns structure, not a bare boolean.** Every `GuardType` returns `GuardResult { satisfied: boolean, reasonCode: String, details: Map<String,Object> }` — a general extension of the guard contract, not a prerequisite-specific special case. The prerequisite guard populates `details` with the missing `AccessForm`(s) and their assignee; other guards may return an empty/simple reason or omit detail.

**`TransitionEvaluation` shape:** `{ event, allowed: boolean, authorityMet: boolean, guardResults: List<GuardResult> }`, one per (state, event) candidate.

**API contract: no new endpoint or DTO shape — keep today's contract, compute it correctly.** `getPossibleEvents` keeps returning exactly what it returns today (Negotiation-level `NegotiationEventMetadataDTO` list, Resource-level `List<String>`/HATEOAS lifecycle links) — the only change is that it's now computed by filtering on the engine's `allowed` flag instead of the current hand-rolled `isSecurityRuleMet()` check. An event with an unmet requirement is simply **omitted** from the listing (matches today's "list of currently-allowed events" semantics — no uniform-superset/annotated-blocked variant needed, since we're not introducing a new per-event shape for that). `TransitionEvaluation`/`GuardResult` (above) stay internal to the engine; their detail doesn't need to travel through this endpoint.

**The existing `requirement-{id}`/`submission-{id}` sibling-link pattern carries over, with two fixes and one cleanup.** `ResourceWithStatusAssembler` already builds these independently of the lifecycle links, reading each `Requirement`'s own `Event` association directly — that data is never lost by omitting the blocked event from the lifecycle listing.

1. **Inclusion condition fix.** Today `addRequirementLink` only adds the hint if a matching lifecycle link *already exists* among the links built so far — once lifecycle links are correctly gated (fix above), that condition would always be false for exactly the case we care about, silently dropping the hint along with the dead-click button. Fix: base inclusion on whether the event is *structurally reachable* from the resource's current state (a transition exists from here for this event, per the definition graph), independent of whether the guard passed.
2. **Display fix.** The link's display name currently carries the raw enum event key (`"MARK_AS_AVAILABLE requirement"`) but the frontend never renders it. Set it to the event's human label instead (`Event.label`, available directly once `Requirement` attaches to the new `Event` entity per ticket 01), and update `ResourceItem.vue`'s requirement-link block to actually show it — e.g. "Access Declaration Required for Mark as Available" instead of just "Access Declaration Required."
3. **HAL cleanup (folded in since this code is already being touched).** Stop minting one rel name per row (`requirement-7`, `requirement-9`, ...) and use HAL's actual mechanism for multiple links under one relation — an array-valued rel: `_links.requirement: [{href, title, name}, ...]`, same for `submission`. `ResourceItem.vue`'s `getRequirementLinks`/`getSubmissionLinks` simplify from prefix-scanning `_links` keys to direct `_links.requirement`/`_links.submission` array access.

**Bulk-fetch batching: flagged as a follow-on implementation concern, not designed here** (same pattern as ticket 03's own deferred DB-cost caveats). `ResourceWithStatusAssembler.toModel()` (`ResourceWithStatusAssembler.java:49-56`) is called once per resource by the HATEOAS assembler's default collection loop, yet re-fetches *all* `InformationRequirement`s system-wide and *all* submissions for the negotiation on every single resource — into a `static` field, no less. Real bug, worth fixing, but the batching/bulk-API shape for it is left to implementation time rather than locked in now.

**`InformationSubmission` shape change.** The JSONB `payload`/`resource`/`negotiation`/`editable` shape carries over, plus one addition: a `submittedBy` (`Person`) reference, which does not exist today (confirmed: no creator/audit field on the entity currently) and is required to match a submission against an assignee's audience (person or group membership).

**Scope: extends to the Negotiation lifecycle for free.** The map's Destination already commits to this. Since ticket 01 made `Event` scope-agnostic (it belongs to a `StateMachineDefinition` with scope `NEGOTIATION`|`RESOURCE`), attaching `Requirement` to `Event` rather than to a Resource-specific enum means Negotiation-scope events can carry requirements with no extra modeling work. One direct implication worth flagging for implementation: `InformationSubmission.resource` will need to become optional, since a Negotiation-scope submission has no associated `Resource`.
