# Resource-Network association & conflict/versioning

Type: grilling

Status: resolved

Blocked by: 01, 03

## Question

A Resource can belong to multiple Networks (many-to-many, see `governance/network/Network.java`). Given the definition model from ticket 01, decide:

- How a Resource's applicable state-machine definition is resolved when associated directly vs. via one or more Networks.
- What happens when a Resource belongs to multiple Networks with different definitions — precedence rule, explicit conflict rejection, merge, or something else.
- Versioning: when a definition is edited, does an in-flight negotiation/resource already running the old definition keep running it, or does it move to the new one — and how is that recorded?

## Answer

**Definition families & versioning.** `StateMachineDefinition` rows form **families**: a lineage of versions sharing an immutable `family_key` (set once at family creation, never edited) — this is the stable identity everything else FKs against. `name` (from ticket 01) stays a freely-editable human display label with no identity role; ticket 01 fixed what a definition row looks like but explicitly deferred versioning mechanics to this ticket, so this is additive, not a revision. Exactly one row per family is `active` at a time; publishing a new version is a one-step flip of the active flag, not a bulk re-point of every association.

**Direct vs. Network resolution.** A direct Resource↔family association always wins outright and unconditionally — Network resolution is only consulted when there's no direct association. This keeps a direct association legible as a deliberate, isolated exception rather than something that could still conflict with a Network's family.

**Default fallback.** A Network's family association is optional (nullable) — a Network makes no claim if unset, and is therefore invisible to the conflict check below. A single global default Resource-lifecycle family is the ultimate fallback when a Resource has no direct association and none of its Networks specify one. This mirrors the Negotiation lifecycle's single global definition.

**Multi-Network conflict.** When a Resource belongs to multiple Networks whose families differ (compared by `family_key`, not by resolved version — two Networks pointing at the same family never conflict regardless of which version is currently active), the operation that would create the conflict is **rejected explicitly at write-time**: adding a Resource to a Network, or changing a Network's family assignment, fails with an error naming the conflicting Networks if it would produce a differing-family conflict for any Resource shared between them. Enforced as an **application-level check in `NetworkService`** (consistent with how this codebase already validates business rules — no DB triggers/constraints for cross-entity rules elsewhere), not a database constraint. No priority/precedence field is introduced — conflicts are resolved by an admin action (e.g., giving the Resource a direct override), not an implicit tie-break. **Resources with a direct override are exempt** from this check: a Network-level conflict can't affect a Resource whose definition is already pinned directly, so it can't trigger a rejection.

**Versioning: pin at start.** A `NegotiationResourceLink` (and the Negotiation-level equivalent, on `Negotiation`) records the specific version row resolved at creation time via a `definition_version_id` FK — immutable thereafter. In-flight negotiations/resources keep running the exact version they started on for their entire lifetime, even after a newer version is published and becomes active for new work. This is consistent with this ticket's own immutable-once-active rule and ticket 03's engine cache — an old version is never mutated or discarded while anything still references it.

**Amendment ([Definition version/identity reconciliation](08-version-identity-reconciliation.md))**: ticket 01's `version` field is a per-family, system-assigned incrementing sequence with a display/audit role only (assigned at row creation); ticket 03's cache key is amended to the version row's id alone — so this ticket's `definition_version_id` FK and the engine cache use the same single identifier.

**Amendment (global-default governance — resolves review finding).** The single global default Resource-lifecycle family is designated by an `is_global_default` boolean flag on the **family** (not on a version row), with a partial unique index enforcing exactly one true. Governance is **`ROLE_ADMIN` only** — designating/reassigning the default is a system-wide act in the same tier as owning the single Negotiation-lifecycle definition; Network managers only ever set their own Network's family and can never touch the global default. Reassigning the default = an admin flips the flag from one family to another (no new settings table needed). The default family **versions identically to any other family** — publishing a new active version and pin-at-start behave the same; in-flight work that resolved *through the default fallback* stays pinned to its recorded `definition_version_id`. "Being the default" is a **resolution-time concern only** — it never touches versioning or pinning, and because the flag lives on the family it survives version flips without pointing at a stale row.

**Amendment (conflict-check scope/cost — resolves review finding).** The write-time conflict check is confirmed **exhaustive but expressed as a single set-based SQL query per write, never per-resource Java iteration (no N+1)**. Two write paths: (1) *adding Resources to a Network* — naturally bounded to the added Resources; (2) *changing a Network's family* — inherently must re-check every member Resource, because that member set is exactly what changed resolution. For the change-family case, one query: *among Resources in Network N, is there any that has no direct override and also belongs to another Network whose `family_key` is non-null and ≠ the new family?* — if any row returns, reject naming the conflicting Network(s); the add case is the same query scoped to the added ids. Worst-case O(members) is **acceptable because these are rare admin/manager governance actions, not request-hot-path** — one indexed round-trip handles even large Networks, and no caching / incremental-diff / size-cap machinery is warranted (premature). A **Network priority/precedence** field was reconsidered as a way to eliminate the check (deterministic ordered `resource → highest-ranked network` walk) and **rejected again**: it trades a loud, admin-correctable rejection for *silent* resolution of genuine lifecycle ambiguity, moves the un-surfaced blast radius onto priority-reorder operations, and centralizes governance that reject-at-write leaves distributed — too high a price to avoid a rare, cheap query.
