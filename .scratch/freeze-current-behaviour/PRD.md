# Freeze current behaviour

Status: ready-for-agent

Slab for map ticket [Freeze current behaviour](../state-machine-implementation/issues/01-freeze-current-behaviour.md)
of the [State machine implementation](../state-machine-implementation/map.md) map.

**Slab gate:** a characterization suite that passes against the current Spring Statemachine code,
with **no production code changed**, plus a mechanically generated dump of both Lifecycle
Definition graphs. Those same tests must later pass *unchanged* against the new subsystem.

## Problem Statement

The lifecycle subsystem is about to be replaced wholesale: Spring Statemachine deleted, the graph
moved into relational configuration, four enums removed, and ~60 main-source files across seven
subsystems rewritten to stop naming States and Events as Java constants.

Today there is almost nothing to tell us whether that rewrite preserved behaviour. Of 138 test
files, four touch the lifecycle directly. Nobody can currently answer "does the Negotiation still
move from SUBMITTED to IN_PROGRESS only for an admin, and does that still notify the Resource
representatives?" except by reading Spring Statemachine builder chains by eye.

Worse, the only authoritative statement of what the two graphs *are* is two Java configuration
classes written in a fluent builder DSL. ADR 0009's correctness claim is that its frozen v1 seed
SQL "faithfully reproduces those two classes" — a claim nobody can check without transcribing
20-odd transitions by hand, which is exactly the error-prone step the claim needs to rule out.

So the effort cannot start. Every later slab's verification story depends on an oracle that does
not exist yet.

## Solution

Two artifacts, delivered before any production code changes.

**1. A mechanical dump of both Definition graphs.** A test-scope generator walks the live
`negotiationStateMachine` and `resourceStateMachine` beans and emits their full structure — states,
events, transitions, initial state, security rules, guards and actions — as canonical JSON, plus a
Mermaid diagram generated from that JSON for human review. Generated by walking the beans, never
transcribed by eye.

This one artifact does triple duty and breaks a circular dependency in the ADR set: ADR 0009 puts
the v1 seed SQL in the migration slab, but seeded Definitions are needed as a test fixture from the
moment the Transition Evaluator exists. The dump serves as the parity oracle, the dev/test fixture
source, and the reference ADR 0009's seed SQL is checked against.

**2. A characterization suite** that pins today's observable behaviour at three seams that all
survive the engine swap, so the same assertions can be re-run against the new subsystem as stage 1's
gate.

The central difficulty is that "passes unchanged" is impossible if the tests name the deleted
enums. The suite therefore names States and Events as **strings** and reaches the services through
a thin test-side adapter — the one place that knows today's enum types. At cutover the adapter is
rewritten and the assertions are untouched. See Implementation Decisions.

## Implementation Decisions

### Seams

Three seams, all already present in the test tree. No new production seam is introduced — this slab
changes no production code at all.

| Seam | Surface | What it pins |
|---|---|---|
| Service | `NegotiationLifecycleService`, `ResourceLifecycleService` | transitions, per-role available events, refusal behaviour, the Information Requirement gate, history rows |
| REST | `NegotiationLifecycleController`, `ResourceLifecycleController` | metadata payload shape, the `GET /v3/resource-lifecycle` diagram |
| Domain event | `NegotiationStateChangeEvent`, `ResourceStateChangeEvent` via `@RecordApplicationEvents` | notification firing conditions, spawn, conclusion |

The service seam is primary. The REST seam exists because ADR 0005 changes rel shapes and ticket 04
changes the metadata contract — both need a before-picture. The event seam exists because the
notification handlers switch on enum constants outside any registry and are the likeliest silent
breakage.

### The string-and-adapter rule — the decision the slab turns on

A parity suite that must "pass unchanged" cannot mention a type that gets deleted. Today
`sendEvent` takes a `NegotiationEvent`; after ADR 0002 that enum is gone and ticket 03 has not yet
decided what replaces it.

So: **characterization tests name States and Events only as string literals** (`"SUBMITTED"`,
`"APPROVE"`). All calls go through a single test-scope adapter interface — one method per service
operation, strings in and strings out — whose only implementation today converts string to enum and
delegates. At cutover that implementation is rewritten once; every assertion stays byte-identical.

This deliberately decouples the parity gate from ticket 03's outcome. It is the reason the gate can
be built now, before that decision exists.

The adapter is the *only* test-scope file permitted to name the four enums.

### Forbidden-import enforcement

A test scans the characterization source tree and fails on any import of
`org.springframework.statemachine..*`, or of the four enums outside the adapter. Mechanical
enforcement, because story 24's property silently degrades under review pressure otherwise.

### The graph dump generator

Test-scope, in its own package, and the **only** component in this slab allowed to touch Spring
Statemachine internals — deliberately, because it is a throwaway that is deleted at cutover. It is
a generator, not a parity test.

- Injects both `StateMachine<String, String>` beans by qualifier and walks
  `getTransitions()` plus `getStates()` and `getInitialState()`.
- Per transition records: source, event, target, kind, security rule attributes and comparison
  type, actions, guard.
- **Guard and Action identity by reflective unwrap.** SSM 4.0 exposes `Transition.getGuard()` as
  `Function<StateContext, Mono<Boolean>>` and `getActions()` as a collection of similar lambdas —
  not the `Guard` / `Action` beans. The generator recovers the underlying bean class by reflecting
  on the lambda's captured field and **throws if unwrap fails**, rather than degrading to a weaker
  artifact. There are three Actions and one Guard in total, so the blast radius is small. A
  half-faithful dump must never ship, because faithfulness is the entire value.
- Emits `negotiation-graph-v1.json` and `resource-graph-v1.json` (canonical, stable key order) and
  `graphs-v1.mmd` (generated from the JSON) under `backend/src/test/resources/lifecycle/`.
- The artifacts are **committed**, and a test regenerates and asserts equality against the
  committed copies. While Spring Statemachine still lives, that test is drift protection; it is
  deleted with the generator at cutover.

### Two structural findings the dump must adjudicate

Both were found while charting this slab and are recorded so implementation confirms rather than
rediscovers them.

**`NegotiationIsApprovedGuard` is probably dead.** It is attached only by
`transitions.withExternal().guard(negotiationIsApproved())` at `ResourceStateMachineConfig.java:117`
— a transition fragment with no source, event or target. The real "Negotiation must be IN_PROGRESS"
check is imperative, in `ResourceLifecycleServiceImpl.getPossibleEventsForCurrentStateMachine`. If
the dump shows the Guard on no transition, then ticket 01's requirement to pin "every guard outcome,
including `NegotiationIsApprovedGuard` in both directions" is satisfied instead by pinning the
imperative gate at the service seam, and the finding is reported up to the map — a Guard that never
fires must not be reimplemented in ADR 0002's registry.

**`DRAFT` may be unreachable as an entry state.** The Negotiation graph declares `SUBMITTED` initial
while also defining `DRAFT → SUBMIT → SUBMITTED`. Whether a Negotiation is ever observably in
`DRAFT` is an empirical question the dump plus a service-seam test settle. It matters because ADR
0009's seed must reproduce whichever is true.

### Intended deltas, not parity

ADR 0005 deliberately changes two behaviours. Pinning them as parity would freeze the bugs the ADRs
exist to fix, so they live in a separately named test class asserting **today's** behaviour, so the
cutover slab has an explicit thing to flip:

- `getPossibleEvents` today lists Events that then fail on click; ADR 0005 omits blocked Events.
- The requirement hint links in `ResourceWithStatusAssembler`: inclusion becomes structural
  reachability, display name becomes the Event's label, and per-row `requirement-7` rels collapse
  into array-valued rels.

### Scope correction carried up to the map

The map's verified fact "No seed, demo or test SQL exists anywhere... zero fixtures" is **false**.
`backend/src/main/resources/db/test/migration/R__Initial_data.sql` and
`db/dev/migration/R__Initial_data.sql` are repeatable Flyway seeds wired in through
`application-test.yaml`, and they already populate `negotiation.current_state`,
`negotiation_resource_link.current_state`, `negotiation_lifecycle_record` and
`negotiation_resource_lifecycle_record`. This slab builds on that seed via
`@IntegrationTest(loadTestData = true)`. The map and ticket 06 are corrected accordingly.

## Testing Decisions

**What makes a good test here.** Only externally observable behaviour: what the service returns,
what it throws, what rows exist afterwards, what application events fire, what JSON the endpoint
produces. A test that mentions a `StateMachine` bean, a `StateContext`, a `PersistStateMachineHandler`
or a persist listener is worthless post-cutover and is rejected by the forbidden-import test. The
one sanctioned exception is the dump generator, which is throwaway by design.

**Modules under test.** `NegotiationLifecycleService` and `ResourceLifecycleService`; the two
lifecycle controllers; the lifecycle-keyed `NotificationStrategy` handlers, observed through
recorded events rather than invoked directly; the two `*LifecycleRecord` entities as written by real
transitions.

**Prior art.**

- `integration/service/NegotiationLifecycleServiceImplTest` (580 lines) is the closest model and the
  main pattern source: `@IntegrationTest(loadTestData = true)`, `@RecordApplicationEvents`,
  `@WithMockNegotiatorUser(id = 109L, authorities = "ROLE_ADMIN")` and `@WithUserDetails` for role
  variation, Awaitility for the asynchronous persist path, `@DirtiesContext` after each method.
- `integration/api/v3/LifecycleInfoTests` (86 lines) for the REST seam.
- `notification/internal/*HandlerTest` for handler-level expectations.
- `unit/model/NegotiationLifecycleRecordTest` and `NegotiationResourceLifecycleRecordTest` for the
  history entities.

**Asynchrony.** `sendEvent` drives the persist handler through
`handleEventWithStateReactively(...).subscribe()`, and the conclusion listener runs
`AFTER_COMMIT` in a new transaction. Assertions on downstream effects must use Awaitility with a
bounded timeout, following the existing test's lead — never a bare sleep, and never an assertion
made immediately after the call.

**Only the handlers that actually key on lifecycle identity are in scope.** Of the eight
`NotificationStrategy` implementations, `NegotiationInProgressHandler` (IN_PROGRESS),
`NegotiationSubmissionHandler` (SUBMITTED), `NegotiationStatusChangeHandler`,
`ResourceStateChangeHandler` and `PendingNegotiationReminderHandler`
(`REPRESENTATIVE_CONTACTED`) do. `NewPostHandler` and `UpdatedResourcesHandler` do not key on state,
and `NewNegotiationHandler` keys on a non-lifecycle event. Ticket 01 says "seven handlers"; the
accurate count of lifecycle-keyed ones is five, and only those are pinned.

**Runnable as one selector.** The whole suite lives under a single test package so the parity gate
is one test-runner invocation at every later slab boundary. Use `/focused-backend-tests` for runs;
no full-suite runs unless asked. **There is no `scripts/test-backend.sh` at the repository root** —
that path appears in several early tickets and exits 127. The script ships with the
`focused-backend-tests` skill, at
`/home/claude/.claude/skills/focused-backend-tests/scripts/test-backend.sh`.

## Out of Scope

- **Any production code change.** The slab gate requires it. A characterization suite that needed
  production edits to pass would not be characterizing anything.
- **The frontend.** Standing decision 5 puts frontend repairs in the slab that breaks them,
  verified manually.
- **The 26 test files that reference the four enums.** They churn in the decouple-consumers slab.
  Not this slab's problem.
- **Deciding what replaces the enums.** That is ticket 03. The adapter exists precisely so this
  slab does not need the answer.
- **Where state-triggered behaviour should live.** That is ticket 02. This slab pins where it lives
  *today*.
- **Choosing the migration rehearsal dataset.** That is ticket 06. This slab only corrects the
  factual premise that no seed data exists.
- **Fixing anything found.** The dead Guard, the possibly unreachable `DRAFT`, the duplicated
  `@EventListener` plus `@TransactionalEventListener` on `ResourceStateChangeListener`, and the
  Resource service's silent-noop refusal are all *pinned as they are* and reported. Characterization
  freezes behaviour; it does not improve it.
- **Generating ADR 0009's seed SQL.** The dump is its reference; whether the SQL is generated from
  the dump belongs to the migration slab.

## Further Notes

- Spring Statemachine is at 4.0.0 (`spring-statemachine-core`, `-recipes-common`, `-starter`), 27
  classes under `negotiation/state_machine/`.
- The two graphs as read from source: Negotiation has 6 states and 8 transitions with 3 Actions and
  two `ROLE_ADMIN`-secured transitions; Resource has 13 transitions secured by `isAdmin`,
  `isRepresentative` or `isCreator`. The dump supersedes this hand count — it is recorded only so a
  wildly different dump is treated as suspicious.
- The two machines evaluate security differently: the Negotiation machine enables
  `withSecurity()` and its service matches rule attributes against Spring roles, while the Resource
  machine does **not** enable security and its service reimplements rule evaluation imperatively in
  `isSecurityRuleMet`, including a `NullPointerException`-to-`creatorId = 0L` fallback and a branch
  that treats an absent `Authentication` as admin. Pin the observable outcomes; do not tidy.
- `ResourceLifecycleServiceImpl.getStateMachineDiagram` recurses through transitions and can revisit
  targets, so its output is path-shaped rather than graph-shaped. Pin the response as-is; a faithful
  post-cutover reimplementation is the cutover slab's problem.
- Ticket 04 names three global metadata DTOs; there are four —
  `NegotiationStateMetadataDto`, `NegotiationEventMetadataDTO`, `ResourceStateMetadataDto`,
  `ResourceEventMetadataDto`. All four endpoints are pinned here.
- `backend/CONTEXT.md` vocabulary is binding, `_Avoid_` lines included: Transition Evaluator not
  engine, Lifecycle not workflow, Audience not assignee.
