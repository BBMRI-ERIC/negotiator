# 0009 — Forward-only convert-in-place migration, stop-the-world

_Source ticket: [Migration / rollout path](../../../.scratch/state-machine-redesign/issues/11-migration-rollout-path.md)._
_Implementation is follow-on work — nothing here is built yet; no migration file exists._

Everything above describes a target schema. This is how production data reaches it: one Flyway cutover that seeds a v1 Definition Family per Lifecycle, pins all in-flight work to it, and re-homes Information Requirements and history.

**Convert in place, forward only.** Because Spring Statemachine is deleted outright (0001) there is no run-both-engines option — the migration that seeds definitions and backfills pins has to land with the cutover deploy. No legacy columns are retained "for rollback": a frozen copy goes stale the moment new code processes a Transition, which would mean dual-writing a subsystem we are deleting. Flyway 11 Community has no `undo` in any case, so **rollback is restoring the pre-deploy snapshot**, accepting the loss of anything processed after the deploy — inherent to snapshot rollback, and the reason the window is kept short.

**Live state stays an authoritative VARCHAR with no FK.** `negotiation.current_state` and the resource-link state column keep owning live state as plain strings, resolved to a `State` row through the natural key of the Definition Version Pin plus the state name. A string plus a pin cannot drift the way an FK to `state.id` could, since an FK could point at a `State` belonging to a different version than the pin. Their only changes are gaining the pin and losing the now-obsolete CHECK constraint. This is what confines 0008's FK conversion to the audit tables.

**Two v1 families are seeded from raw, frozen SQL** — explicit INSERTs in a committed `V*.sql` file, matching the repo's fifty existing SQL migrations, fully deterministic, and immune to the classic Flyway-Java-migration trap where a migration rots as entity code evolves. The seed is a faithful transcription of the current two configuration classes: states, events, transitions, required authorities, initial and terminal flags, the definition-level `NEGOTIATION_APPROVED` Guard wiring (0005) and the single `SPAWN_RESOURCE_LIFECYCLES` Action on the approval Transition (0007). The Resource family carries `is_global_default` (0004), which is what makes resolution total at migration time, when no direct or Network associations exist yet. A canonical importable definition file for admins is a separate downstream feature; the seed may one day be generated from one, but it is committed as frozen SQL.

**Every Negotiation and every `NegotiationResourceLink` pins to v1, drafts included.** All pre-migration work ran under the one hardcoded Lifecycle, so all of it pins to the one seeded version; a draft that submits later keeps that pin, consistent with pinning at start. Mechanically: add the column nullable, update everything, set NOT NULL — coverage is total.

**`APPROVED` and `RETURNED_FOR_RESUBMISSION` survive as Legacy States.** Both are unreachable in current code, but both are enshrined in live and audit CHECK constraints, which means older code once wrote them and production history very likely still holds them. So "dropped" (0002) means *removed from the active transition graph*, not physically absent: the seed creates them as transition-less, non-initial `State` rows — nothing flags them, what makes them unreachable is simply that no Transition targets them, the same shape the Override Event already has. History stays faithful, live strings still resolve, 0008's FK lands, and the deploy is never blocked. Dropped *Events* are a different case and are fully omitted: an Event leaves no data residue, because history records the resulting State and not the Event that caused it (0008). Remapping the old values onto surviving ones was rejected as distorting immutable history, and asserting-and-failing was rejected because the data is almost certainly there, so it would just block the deploy.

**Information Requirements re-home by name.** An `event_id` FK is added and backfilled by matching the legacy `for_event` string against the v1 Resource definition's Event of the same name, then `for_event` is dropped; the access-form reference carries over unchanged. Every legacy row gets Audience `RESOURCE_REPRESENTATIVES` with empty params and Quantifier `ANY` — the faithful reproduction of today's implicit "any one of the Resource's own representatives" (0006). `submittedBy` is NULL for all legacy submissions, because the table never recorded an author and inferring one would be fabricated data. The only cost is a Resource sitting exactly at a not-yet-fired requirement-bearing Event with a pre-existing submission: nothing counts toward the audience check, so a representative resubmits once. Every already-advanced Resource is a committed fact that is never re-evaluated, so it is unaffected.

**Audit history backfills by same-name join** to the matching v1 definition — Negotiation records to Negotiation v1 States, Resource records to Resource v1 States, Legacy States included. "Which version did history run under?" is trivial, because there is exactly one, which is why no per-record version reasoning is needed (0008).

**The cutover is stop-the-world.** The migration is breaking for old code — it drops `information_requirement.for_event`, which the current resource lifecycle service reads, and drops CHECK constraints old code assumes — so old and new instances cannot coexist against the migrated schema. Old instances are drained and stopped, then the new version starts and Flyway runs on boot. A short maintenance window is proportionate to replacing a core subsystem, and engineering a rolling-safe expand/contract with a compatibility shim in code we are deleting is not worth it. In-flight work is safe across it: state lives in the database, and every change to it is additive.

**Packaging is two migrations.** First, additive DDL on its own — the definition, State, Event, Transition, wiring and requirement tables, plus the new columns added nullable — which is harmless if it lands alone. Then the data cutover as one atomic file, since PostgreSQL makes DDL and DML transactional and a half-migrated database is the one outcome to rule out. Its order is: pre-flight asserts first, raising before anything destructive so a surprise value aborts with the snapshot intact; then the v1 seed; then the backfills (pins, audit `state_id`, requirement re-homing); then NOT NULL on the now-populated columns; then the drops — `for_event`, the obsolete CHECKs, and the converted audit column. Every id reference goes through a name or family-key subquery rather than a hardcoded seed id, so nothing depends on which sequence values PostgreSQL hands out. Flyway's version tracking means the file never re-runs, so no idempotency guards are needed.
