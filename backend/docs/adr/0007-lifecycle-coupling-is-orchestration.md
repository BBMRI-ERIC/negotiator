# 0007 — Lifecycle coupling is orchestration over the stateless evaluator

_Source ticket: [Lifecycle coupling: fan-out / fan-in](../../../.scratch/state-machine-redesign/issues/09-lifecycle-coupling.md)._
_Implementation is follow-on work — nothing here is built yet; coupling still lives in `NegotiationInProgressHandler` and the link-initialization scatter._

Everything so far designs a single Definition Version in isolation, but the behaviour that matters most is the coupling: on approval a Negotiation's Resource Lifecycles begin, and when they have all finished the Negotiation concludes by itself. That is hardcoded Java today.

**Coupling is an orchestration layer over the Transition Evaluator, not an engine feature and not a new table.** No coupling rows link a parent to its children and no parent→child instance is persisted; fan-in is a query over the Negotiation's existing Resources and their state columns. The evaluator stays the indifferent stateless component of 0001. A first-class `Coupling` entity was rejected: it re-encodes a relationship that is structurally fixed — a Resource belongs to its Negotiation, and no admin should be able to say otherwise — while adding a forgotten-row failure mode in exchange for flexibility nobody wants.

**There is exactly one primitive: an Orchestration Trigger re-attempts a definition's System Events from whatever State the Lifecycle is currently in, and the Evaluation Pipeline decides whether any fires.** Two things can pull it. A committing Transition elsewhere is the one specified here. A clock tick is declared as reusing the identical path — the primitive is ready for it — but its scheduler plumbing is deliberately not designed, and is built when the features that need it (requirement reminders, expiry) are.

**"Automatic" is the distinct `SYSTEM` Required Authority (0002), not an overload of `NONE`.** An Event is machine-fired if and only if its authority is `SYSTEM`. Because authority is the first thing the pipeline checks, a System Event fails for every human caller: it never appears in Possible Events and can never be fired over REST. Auto-fire versus wait-for-a-human is then genuine configuration — flip `SYSTEM` to `IS_ADMIN` and the same Event becomes a manual admin action — but expressed as a typed value rather than as the absence of a gate. `NONE` means "any human may fire this"; `SYSTEM` means "no human at all", and conflating them would have made every open Event machine-fireable.

**Feedback is implicit and zero-config.** After any Resource Transition in a Negotiation commits, a post-commit hook re-attempts that Negotiation's System Events from its current State. Nothing configures which Event the children feed. Post-commit rather than inline keeps parent and child atomicity separate and preserves the evaluator boundary; the brief window in which a Negotiation is concludable but not yet concluded is exactly today's, so it is not a regression.

**Conclusion is a System Event plus a `TERMINAL_AGGREGATION` Guard.** The Guard takes no params: it passes when every Resource of the Negotiation is in a terminal State. "Terminal" cannot be a hardcoded list of state ids, because Resources in one Negotiation may run different definitions — so the Guard asks each Resource's own pinned Definition Version whether its current State carries the terminal flag. A configurable quantifier (`ANY`, `N-of-M`) is not planned; there is no case for concluding a Negotiation while Resources are still running, and because Guard params are jsonb (0002), adding one later needs no migration.

**Spawn is a wired-once Action.** `SPAWN_RESOURCE_LIFECYCLES` is an ordinary Action strategy on the transition-scoped Action registry, with today's scattered initialization logic relocated into it. Its wiring is the only configurable part and is configured exactly once — one row on the sole Negotiation definition's approval Transition. Resource definitions are the *targets* of Spawn and carry no Spawn configuration at all, so adding a new Resource family wires nothing. Making it a wired Action rather than hardcoding entry-to-`IN_PROGRESS` is what honours 0005's point that a Network may legitimately want Resource work to start before approval. Per requested Resource the Action does three things atomically in the approval transaction: resolve the Definition Family (0004), pin the resolved version on the `NegotiationResourceLink` (0003), and set the State to that definition's initial one. Pinning happens at Spawn rather than at Negotiation creation because that is when a Resource Lifecycle actually starts — so resolution runs against the final Resource set and the versions active at approval time. Because resolution is total (0004), Spawn cannot half-initialize.

**Double-fire safety comes from the graph first and a lock second.** Two Resources finishing at once each run the post-commit hook, but once the first has moved the Negotiation to its concluded State, the second attempt's source State no longer matches and the attempt is a natural no-op — a System Event from the wrong State is simply not a valid move. A pessimistic row lock on the parent Negotiation during an attempt then serializes the two, so the loser re-reads the new State and no-ops cleanly rather than doing duplicate work and writing a duplicate history row. The State check is for correctness; the lock is for waste.

Two things are deliberately left out. **Outcome-sensitive conclusion** — routing all-delivered and all-unavailable to distinct terminal outcomes — is a lifecycle and product change beyond this redesign, whose baseline is today's single outcome-blind conclusion; it is *accommodated as later configuration* (additional mutually exclusive System Events from the in-progress State, plus new States) rather than foreclosed. **A Resource linked to an already-running Negotiation** would bypass Spawn and start unpinned; today's model links Resources up front, so this is flagged for the implementation effort rather than designed here.
