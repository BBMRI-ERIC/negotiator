# 0006 — Information-requirement Audience and satisfaction are derived, never stored

_Source tickets: [Information-requirement audience, aggregation & contact](../../../.scratch/state-machine-redesign/issues/10-info-requirement-audience-contact.md), [Information requirements as first-class model](../../../.scratch/state-machine-redesign/issues/05-info-requirements-model.md) (assignee → Audience)._
_Implementation is follow-on work — nothing here is built yet._

The requirement check has a place in the pipeline (0005) but nothing yet says *who* is asked, *how many* must answer, or *how they are told*. Today there is no answer at all: satisfaction means "some submission exists", with an implicit and undisambiguated audience of the Resource's representatives.

**There is no per-occurrence row for an Information Requirement anywhere.** Audience and Quantifier are configuration on the `Requirement`; satisfaction is computed from `information_submission` rows every time it is asked. The Requirement's only states are a derived `PENDING`/`SATISFIED` projection. Making the Requirement its own state machine on a third scope was explored and rejected — a Requirement has no entity to hold a state column the way a Negotiation or a `NegotiationResourceLink` does, so it would have forced exactly the persisted instance this design exists without, in exchange for a two-state machine identical to the boolean.

**Audience is a resolver registry, shaped exactly like 0002's Guard and Action strategies:** an `audience_type` key plus typed `audience_params` jsonb on the `Requirement`, dispatched to a strategy bean. The strategies share one primitive, `resolve(params, context) → Set<PersonRef>`; membership, the denominator and the list to notify all fall out of that single set, which is why a two-method `contains`/`enumerate` interface earns nothing — the audiences in play are small and every consumer wants the whole set. The resolver reads the Evaluation Pipeline's existing context, so there is no new plumbing. Three strategies exist: `RESOURCE_REPRESENTATIVES` (Resource scope only), `NEGOTIATION_CREATORS` (both scopes — a Resource-level requirement may legitimately ask the requester for something), and `IAM_GROUP` with a `groupKey` (both scopes). Each declares which Definition Scopes it serves, and a mismatch is refused when the requirement is saved: wiring `RESOURCE_REPRESENTATIVES` onto a Negotiation-scope Event would resolve to an empty set, an unsatisfiable requirement discovered as a dead click months later.

**The Quantifier is one rule: distinct qualifying members ≥ threshold.** `ANY` sets the threshold to 1, `N_OF_M` to a configured N, `ALL` to the live audience size — the only dynamic one. Counting is by distinct member, so one representative submitting twice counts once, and a submission qualifies only if its `submittedBy` is in the resolved Audience; an out-of-audience submission of the same form is kept but never counts.

**The Audience is re-resolved live, with no snapshot.** Drift is harmless, and this is the load-bearing argument for the whole derive-don't-store position: the requirement gates only the instant an Event fires, and once the Transition commits, the Lifecycle's State is a persisted fact that is never re-derived from satisfaction. So adding a representative can make an Event flicker in and out of the Possible Events listing, but it can never roll back a committed move. Freezing the Audience at notification time was rejected precisely because it would require persisting a per-occurrence audience snapshot.

**Audience Notification is a built-in post-commit stage, not an admin-wired Action.** When a Transition commits into a State, the `NOTIFY_IR_AUDIENCE` stage in the orchestration layer looks one hop out for requirement-bearing Events — the same structural reachability 0005 uses for its hint links — resolves each Audience and notifies. It is deliberately structural, paired with 0005's built-in check, so telling people and enforcing on them cannot drift apart; a configurable version's fatal case is an admin who adds a new in-edge, or forgets a row, and produces a requirement nobody is ever told about. It belongs to the orchestration layer rather than the Transition Evaluator because notifying is I/O and the evaluator does none (0001). Exactly-once needs no dedup record: with no memory of having notified anyone, re-entry notifies again, which is made correct rather than merely tolerable by notifying only the members who have not yet submitted — the first entry tells everyone, a re-entry nags the stragglers, and a re-entry after satisfaction tells nobody.

**The governing invariant: a state is derivable exactly when every action that enters it leaves a domain fact.** Submitting leaves a row, so `SATISFIED` is derivable. Notifying an Audience leaves nothing by design — which is safe only because it is a fire-and-forget side effect and not a state, so nothing ever has to derive whether it happened. Any future action must respect this: waiving writes a waiver record, and reminders or expiry write a `notified_at` that makes a `NOTIFIED` state derivable. Both are additive; neither is built now.

The `IAM_GROUP` resolver's *interface* is settled here. How LS-AAI group membership is actually fetched, mirrored, cached and refreshed is out of scope for this redesign and returns as its own effort — the plumbing does not change anything above.

This ADR does not restate the pipeline's position or ordering (0005).
